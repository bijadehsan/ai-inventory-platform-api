# ADR 0002: Database access: SQLAlchemy ORM + Alembic migrations

- **Status:** accepted
- **Date:** 2026-10-31

## Context
The backend needs to read and write PostgreSQL safely (no SQL injection), with transactions, connection pooling and async support for FastAPI.

## Options considered
| Option | .NET equivalent | Notes |
|---|---|---|
| Raw SQL with a driver (psycopg/asyncpg) | ADO.NET / Dapper | Full control, lots of boilerplate, SQL in strings |
| SQLAlchemy Core (query builder) | Dapper + a query builder | Composable, typed, no object tracking |
| **SQLAlchemy ORM** | **EF Core** | Entity classes, unit of work, migrations via Alembic |
| SQLModel | — | One class = DB table + API schema; conflicts with ADR-0001 layering |

## Decision
**SQLAlchemy 2.1 ORM (async) + Alembic migrations**, used only inside repositories. Driver: **asyncpg**. psycopg 3 was tried first (SQLAlchemy 2.1's default), but its async mode can't run on Windows' default event loop (ProactorEventLoop); asyncpg works on both Windows and Linux without workaround code and is the most common async driver with FastAPI.
Hand-written SQL (or SQLAlchemy Core) is allowed for complex reports, also inside repositories.

## Rejected alternatives
- **Raw SQL only:** too much boilerplate for CRUD; untyped strings.
- **SQLModel:** merges DB models with API schemas; our API and table shapes will diverge.

## Consequences
- An EF-Core-like workflow: model class → autogenerated migration → upgrade.
- Risk of hidden N+1 queries: mitigated by logging the SQL in development and loading related data explicitly.
- **10x/100x:** unchanged at this layer; scaling comes from indexes, connection pooling and read replicas, not from changing the access style.
